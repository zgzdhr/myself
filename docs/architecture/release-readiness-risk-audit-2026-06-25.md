# 项目完整度、发布风险与双版本基础设施审计

日期：2026-06-25
状态：当前发布前问题清单。后续新 session 在继续发布、安全、云端或国内部署工作前，应先阅读本文件。

## 1. 文档目的

本文件用于长期保存当前项目已经发现但尚未全部解决的问题，避免后续 session
只看到已完成功能，又重复扩展新能力，忘记产品化和发布风险。

当前结论：

> 项目已经是可以个人真实试用的 Beta，不再只是 Demo；但距离公开发布仍有明显差距。

当前最重要的工作不是继续增加 AI 功能，而是完成：

- 服务安全；
- 数据恢复；
- 正式应用身份和签名；
- 隐私与账号注销；
- 国内网络和国内基础设施；
- 长期真机稳定性；
- 项目文档与真实代码状态同步。

## 2. 产品定位与当前主闭环

项目定位仍然是：

> 一个面向 Android 与 iOS 的个人记忆与行动整理 App。用户用自然语言输入任务、
> 状态、经历、偏好和问题，系统用 AI 解析为结构化数据，经用户确认后写入个人
> 记忆，并在后续建议、复盘和时间规划中调用这些记忆。

当前已经形成的主闭环：

```text
自然语言输入
→ /parse 结构化解析
→ schema 校验
→ 自动保存或用户确认
→ 本地 SQLite 正式记录
→ 首页今日行动与建议
→ /review 每日复盘
→ /plan AI 时间规划草稿
→ 用户编辑、确认或删除
```

三个 AI 入口的职责已经合理拆分：

```text
/parse   这句话应该整理成什么？
/review  今天发生了什么，有什么值得复盘？
/plan    今天的任务和状态可以怎样安排？
```

不要重新把复盘、规划、知识库和长期教练逻辑塞回 `/parse`。

## 4. 国内版与国际版的基础设施原则

### 4.1 关键判断

国际版当前使用的 Vercel 和 Supabase，不是整个产品永久绑定的唯一基础设施。

后续应按“双版本、同核心”理解：

```text
同一套 Flutter 产品核心
├── 国际版
│   ├── API：Vercel 或其他海外部署
│   ├── 账号 / 数据库：Supabase
│   └── AI：海外网络可访问的 DeepSeek API
│
└── 国内版
    ├── API：腾讯云 / 阿里云 / 百度智能云等国内 HTTPS 服务
    ├── 账号：国内自建或国内云认证服务
    ├── 数据库：国内 PostgreSQL / 云数据库
    └── AI：国内网络稳定可访问的模型服务
```

国内版的具体云厂商尚未最终决定。候选可以包括：

- 腾讯云；
- 阿里云；
- 百度智能云；
- 其他满足成本、备案、网络和数据库需求的国内服务。

在正式选型前，不应把业务代码继续深度绑定到 Supabase 专属能力。

### 4.2 应保持统一的部分

国内版和国际版尽量共享：

- Flutter 页面和交互；
- 本地 SQLite 数据模型；
- `/parse`、`/review`、`/plan` 的请求和响应合同；
- ContextBuilder 规则；
- 任务、状态、事件、画像、复盘和时间规划的领域模型；
- 用户确认、编辑、删除和来源解释原则；
- AI 输出 schema 校验；
- 测试样例和隐私边界。

### 4.3 应允许替换的部分

以下能力应通过接口或配置替换，不应散落在页面代码里：

- 登录认证 provider；
- 云端数据库 provider；
- 云同步实现；
- API Base URL；
- AI provider 和模型配置；
- 文件存储；
- 短信、邮箱或验证码服务；
- 错误监控和日志服务。

建议长期边界：

```text
业务页面
→ AuthService / CloudSyncService / AI Client 抽象
→ 国际版实现 或 国内版实现
```

当前项目已经有 `CloudAuthService`、`CloudSyncService` 和 AI Client 抽象，
方向是正确的；后续国内版应增加新的实现，而不是把国际版实现硬改成国内版。

## 5. P0：公开发布前必须解决的问题

### 5.1 AI API 缺少用户鉴权和限流

当前国际版 Vercel 上的 `/parse`、`/review`、`/plan` 是公开接口。

风险：

- 任何知道接口地址的人都可能调用；
- 可能恶意消耗 DeepSeek 额度；
- 无法按用户统计或限制调用；
- 无法封禁异常用户；
- CORS 开放不能代替鉴权。

国际版候选方案：

- 使用 Supabase 登录 token 验证用户身份；
- 增加用户级和 IP 级限流；
- 增加每日调用额度；
- 保留 `/health` 为公开接口。

国内版候选方案：

- 使用国内账号系统签发的 access token；
- API 服务统一验证 token；
- 使用 Redis 或数据库记录用户级限流；
- 在腾讯云 / 阿里云 / 百度云网关或应用层增加防刷规则。

核心原则：

> API 鉴权应依赖统一的用户身份合同，而不是把业务 route 写死为 Supabase。

### 5.2 云端能力目前只是单向上传，不是完整同步

当前国际版实现：

```text
本机 SQLite → Supabase
```

当前没有：

- 从云端恢复到新手机；
- 双向同步；
- 多设备冲突处理；
- 本地删除向云端传播的完整保证；
- 云端删除向本地传播；
- 同步断点和失败重试队列。

风险：

- 用户卸载 App 后可能无法恢复数据；
- 换手机后无法从云端重建本地数据库；
- “同步完成”容易让用户误以为数据已经可恢复；
- 多设备编辑可能产生覆盖或冲突。

发布前最低要求：

1. 明确页面文案是“上传云端副本”还是“云同步”；
2. 至少实现新设备从云端恢复；
3. 恢复前显示将导入的数据量；
4. 规定本地已有数据与云端数据冲突时如何处理；
5. 恢复过程可失败重试，不产生重复记录。

国内版也应遵循同一恢复合同，但数据库可以替换为国内 PostgreSQL / 云数据库。

### 5.3 正式应用身份和签名尚未完成

Android 当前问题：

- application ID 仍是 `com.example.mobile`；
- App 名称仍是 `mobile`；
- Release 仍使用 debug signing；
- Release manifest 仍允许广泛明文 HTTP；
- 尚未完成正式图标、名称和签名管理。

iOS 当前问题：

- Bundle ID 仍是 `com.example.mobile`；
- 显示名称仍接近默认 `Mobile/mobile`；
- 没有 Apple Developer 正式签名；
- 没有真实 iPhone 发布链路验证。

发布前要求：

- 确定正式中英文 App 名称；
- 确定唯一 Android application ID 和 iOS Bundle ID；
- 创建并安全保存 Android keystore；
- 配置 iOS Developer Team、证书和 provisioning；
- Release 只允许 HTTPS；
- 分离 Debug、国内 Release、国际 Release 构建配置；
- 不把签名密码和私钥提交到 Git。

### 5.4 隐私与账号注销没有闭环

当前数据包含：

- 原始输入；
- AI 解析结果；
- 任务和生活事件；
- 情绪、身体和短期状态；
- 长期画像；
- 复盘和时间规划。

发布前至少需要：

- 正式隐私政策；
- 首次使用或首次上传 AI 时的清晰说明；
- 说明哪些数据只在本地；
- 说明哪些数据会上传云端；
- 说明哪些数据会发送给 AI；
- 数据导出；
- 删除云端个人数据；
- 注销账号；
- 注销后 session 失效处理；
- 明确备份和恢复的保留时间。

国际版和国内版必须分别核对各自服务商、地区和发布平台的合规要求。

不要直接复制一份通用隐私政策；最终内容必须与真实数据流一致。

## 6. P1：内测和稳定性问题

### 6.1 客户端和服务端超时不一致

当前大致配置：

| 能力 | 手机等待 | API / 模型等待 |
|---|---:|---:|
| `/parse` | 12 秒 | 20 秒 |
| `/review` | 18 秒 | 25 秒 |
| `/plan` | 20 秒 | 25 秒 |

风险：

- 手机已经显示失败，服务端仍继续调用模型；
- 用户重复点击，产生重复请求和额外成本；
- API 成功返回但客户端已断开。

建议：

- 客户端等待时间略大于服务端；
- 请求增加唯一 request id；
- 生成类操作防止重复点击；
- 研究客户端断开后是否取消上游模型请求；
- 对 `/review` 和 `/plan` 提供明确重试入口。

### 6.2 时区固定为 `Asia/Shanghai`

当前适合国内使用，但用户出差到其他时区时可能出现：

- “今天 / 明天”解析偏差；
- 提醒时间错误；
- 复盘日期范围错误；
- 时间规划落在错误日期。

建议后续从设备读取真实时区，并把时区作为请求合同传给 API。

### 6.3 三星等 Android 后台提醒可靠性

当前提醒采用系统本地通知和非精确调度。

风险：

- 三星省电策略可能延迟提醒；
- 用户拒绝权限后缺少持续引导；
- 系统重启和 App 更新后的提醒恢复需要持续真机验证；
- 没有提醒提前量和每日复盘提醒。

当前不要立刻增加复杂提醒功能，应先验证：

- 创建未来任务；
- 修改时间；
- 完成、取消、删除；
- 手机重启；
- App 更新；
- 后台省电；
- 不同 Android 厂商。

### 6.4 用户设置未全部持久化

“复盘结果参与首页建议”目前运行时生效，但 App 重启后恢复默认开启。

后续需要本地设置表或轻量 preference storage。

### 6.5 API 完整测试仍有已知挂起

`apps/api/test/privacyLogging.test.ts` 存在 server / fetch 生命周期挂起问题。

这不是当前业务错误，但会影响一键全量验证和 CI 可信度，应单独修复。

### 6.6 文档落后于代码

README 和部分架构文档仍写着：

- 下一步做 `/review`；
- 复盘页只是入口骨架；
- 复盘参与建议尚未完成。

但实际代码已经完成：

- `/review`；
- Phase 5C 复盘弱上下文；
- `/plan`；
- 时间规划页面；
- 手动同步 summary 和 plan。

后续需要统一更新：

- `README.md`；
- `AGENTS.md` 当前下一步；
- `docs/architecture/current-verification.md`；
- `docs/architecture/phase-5-task-map.md`；
- “我的”页相关描述。

## 7. P2：架构和维护风险

以下文件已经明显偏大：

| 文件 | 大致行数 | 当前压力 |
|---|---:|---|
| `extracted_items_controller.dart` | 1000+ | 提交、保存、撤销、任务更新匹配混在一起 |
| `profile_settings_screen.dart` | 1100+ | 页面、登录、同步、API 检测和设置详情混在一起 |
| `review_screen.dart` | 900+ | 数据读取、AI 请求、保存、编辑、删除和 UI 混在一起 |
| `schedule_plan_screen.dart` | 1000+ | 规划生成、数据库写入、时间块编辑和 UI 混在一起 |
| `app_database.dart` | 800+ | 多种数据表查询和写入集中 |

当前不是“屎山”，因为：

- 领域模型清楚；
- AI 入口已拆分；
- 测试数量较多；
- 数据状态边界明确。

但后续新增功能前应逐步提取：

- ReviewService；
- SchedulePlanRepository；
- UserPreferenceStore；
- AccountDataService；
- CloudBackup / CloudRestore service；
- API authentication middleware；
- rate limiter。

不要为了“架构漂亮”一次性大重构。只在新增真实能力时顺手拆对应职责。

## 8. 产品闭环仍缺少的部分

当前已经有：

```text
记录 → 建议 → 复盘 → 规划
```

但还没有完整形成：

```text
计划 → 执行 → 结果 → 复盘 → 下一次调整
```

具体缺口：

- 时间规划块没有独立提醒；
- 规划块和任务完成状态没有执行反馈；
- 复盘建议不能一键加入任务；
- 没有记录“计划是否执行”；
- 没有比较计划时间与实际结果；
- 没有周级别复盘。

这些是未来产品价值方向，但当前优先级低于安全、恢复、发布和真机稳定。

## 9. 推荐实施顺序

### 阶段 A：先确定双版本基础设施合同

1. 保留国际版 Vercel + Supabase，不删除现有部署；
2. 选择国内云厂商前，先定义 provider 无关接口；
3. 明确国内版账号、数据库、API 和 AI provider 候选；
4. 统一国内版与国际版的数据 schema 和 API 合同；
5. 设计构建配置：

```text
internationalRelease
domesticRelease
debug
```

### 阶段 B：发布阻塞修复

1. API 鉴权；
2. 用户级限流；
3. 云端恢复；
4. 数据删除和账号注销；
5. 包名、App 名称、图标和正式签名；
6. Release HTTPS；
7. 正式隐私政策。

### 阶段 C：国内版部署

1. 选择腾讯云 / 阿里云 / 百度智能云等；
2. 购买服务器或应用托管服务；
3. 准备域名、备案和 HTTPS；
4. 部署 `/parse`、`/review`、`/plan`；
5. 接入国内账号和数据库实现；
6. 中国大陆手机流量真机验证；
7. 保留国际版配置，不互相覆盖。

### 阶段 D：稳定性与发布验收

1. Android 多厂商提醒测试；
2. Android 正式签名包；
3. iOS 真机与签名；
4. 登录、上传、恢复、删除、注销全流程；
5. 弱网、超时、重复请求和 AI 失败；
6. 隐私政策与真实数据流逐项核对；
7. 更新所有项目文档。

### 阶段 E：产品增强

发布阻塞解决后，再考虑：

- 复盘建议加入任务；
- 时间规划提醒；
- 计划执行反馈；
- 周复盘；
- 双向同步和冲突合并；
- 外部日历；
- 电脑端分析界面；
- 可控记忆归档和恢复。

## 10. 新 session 开始前的检查清单

当后续用户说“继续发布”“做国内版”“做云同步”“做账号系统”时，先确认：

1. 当前做的是国内版还是国际版？
2. 当前 API provider 是谁？
3. 当前账号 provider 是谁？
4. 当前数据库 provider 是谁？
5. 是否会改变现有国际版？
6. 是否涉及真实云端写入或删除？
7. 是否需要用户提供云账号、域名、备案或签名材料？
8. 是否已经定义数据恢复和冲突规则？
9. 是否更新了本文件和任务地图？

不要默认：

- Supabase 是国内版数据库；
- Vercel 是国内版 API；
- 国际版方案可以直接复制到国内；
- “上传成功”等于“可以恢复”；
- “Release APK 构建成功”等于“可以上架”。

## 11. 当前建议的下一步

下一步不应直接开始大规模改 Supabase 或 Vercel。

建议先做一份“国内版 / 国际版基础设施接口设计”，明确：

- Flutter 如何选择环境；
- AuthService 统一合同；
- CloudBackup / CloudRestore 统一合同；
- API token 统一合同；
- 国内和国际数据库保持哪些相同字段；
- 哪些 provider 能独立替换。

设计确认后，再分别实现：

```text
国际版：Supabase + Vercel
国内版：国内账号 + 国内数据库 + 国内 HTTPS API
```

这样可以避免现在为国际版写死一套逻辑，过几天做国内版时又整体推翻。
